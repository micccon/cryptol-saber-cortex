# SABER — High-Level Cryptol Specification

This directory contains a formal specification of the SABER key encapsulation mechanism (KEM) in Cryptol, closely following the [SABER Round 3 specification](https://www.esat.kuleuven.be/cosic/pqcrypto/saber/files/saberspecround3.pdf). It is one of three components in this project — see the root `README.md` for a description of the project as a whole and how the components relate to one another.

This specification prioritizes faithfulness to the formal spec and mathematical correctness over bit-level compatibility with any particular C implementation.

## Overview

SABER is a lattice-based KEM submitted to the NIST Post-Quantum Cryptography standardization process. It is built on the hardness of the Module Learning With Rounding (MLWR) problem and provides IND-CCA2 security via a Fujisaki-Okamoto transform applied to an underlying IND-CPA public-key encryption scheme.

This directory contains a complete Cryptol specification of:

- the IND-CPA PKE scheme (`SaberPKE.cry`)
- the IND-CCA KEM scheme (`SaberKEM.cry`)
- all supporting algorithms and helpers (`SaberAlgorithms.cry`, `SaberHelpers.cry`)
- types and constants (`SaberTypes.cry`, `SaberConstants.cry`)
- correctness tests for both PKE and KEM (`SaberPKETests.cry`, `SaberKEMTests.cry`)

The default parameter set is **Saber** (the middle security level). LightSaber and FireSaber can be selected by adjusting the constants in `SaberConstants.cry`.

### A note on `SaberKATTests.cry` and `expand_kats.py`

An early goal of this project was to verify the implementation against the NIST KAT vectors in the `KATs/` directory. `expand_kats.py` parses the `.req` files and expands the 48-byte NIST seeds through an AES-256 CTR DRBG (matching `rng.c` from the SABER reference implementation) to produce the `seedA`, `seedS`, `z`, and `m` inputs used in each KAT. `SaberKATTests.cry` contains the resulting expanded test vectors wired up as Cryptol properties.

However, this effort was ultimately abandoned because the NIST KAT vectors were generated by the C reference implementation, which diverges from the formal SABER specification in several low-level ways — polynomial packing bit order, centered binomial sampling, and component ordering within keys and ciphertexts. Adapting the Cryptol spec to match these arbitrary implementation choices would undermine the value of having a clean formal specification. Both files are retained for reference but should not be taken as a measure of correctness.

It is a future goal of this project to develop a self-contained KAT test harness where the Cryptol spec itself generates its own test vectors — avoiding any dependency on the C reference implementation's arbitrary design choices. This will also serve as a natural bridge between this `HighLevelSpec` component and the `C-Implementation` component of the broader project.

## Prerequisites

[Cryptol](https://cryptol.net) version 3.0 or later is required. Installation instructions are available at [cryptol.net](https://cryptol.net).

To verify the SAT-based properties, a supported SMT solver such as [Z3](https://github.com/Z3Prover/z3) must be installed and on your `PATH`.

## Loading the modules

Start a Cryptol REPL from the `HighLevelSpec/cryptol/` directory:

```
cryptol SaberPKETests.cry
```

or:

```
cryptol SaberKEMTests.cry
```

## Verifying correctness

### PKE roundtrip

The core PKE correctness property states that encrypting then decrypting a message recovers the original message. This is checked in `SaberPKETests.cry` using random testing over arbitrary messages and encryption seeds (with fixed `RandBytes`-generated keys).

Load the PKE tests module and run:

```
SaberPKETests> :set tests=5
SaberPKETests> :check check_PKE_EncDet_Decrypt_roundtrip
```

This tests 5 randomly chosen `(m, encSeed)` pairs. A single test takes several minutes on typical hardware due to the `MatrixVectorMul` and `PolyMul` computations. You may wish to start with fewer tests:

```
SaberPKETests> :set tests=1
SaberPKETests> :check check_PKE_EncDet_Decrypt_roundtrip
```

There are also fixed-input roundtrip checks that run faster:

```
SaberPKETests> check_roundtrip_zeros
SaberPKETests> check_roundtrip_ones
SaberPKETests> check_roundtrip_alternating
SaberPKETests> check_roundtrip_sequential
```

And a zero-seed example that can be verified quickly:

```
SaberPKETests> check_PKE_roundtrip_example
```

### KEM roundtrip

The core KEM correctness property states that decapsulating a ciphertext produced by encapsulation recovers the same session key. This is checked in `SaberKEMTests.cry` over random keys and message seeds.

Load the KEM tests module and run:

```
SaberKEMTests> :set tests=1
SaberKEMTests> :check check_KEM_roundtrip
```

Each KEM test generates fresh random keys and a random message, making this a strong correctness check. Due to the computational cost of the underlying lattice operations, a single test takes approximately 10 minutes on Apple Silicon M1 Pro hardware. Plan accordingly.

Fixed-seed KEM roundtrip checks are also available and run slightly faster since the keys are precomputed at module load time:

```
SaberKEMTests> check_KEM_roundtrip_zeros
SaberKEMTests> check_KEM_roundtrip_ones
SaberKEMTests> check_KEM_roundtrip_alternating
SaberKEMTests> check_KEM_roundtrip_sequential
```

### Sanity checks

Several lightweight sanity checks verify lengths and basic properties of key generation. These run quickly and can be used to confirm the module loaded correctly:

```
SaberPKETests> :prove check_PKE_KeyGen_pk_length
SaberPKETests> :prove check_PKE_KeyGen_sk_length
SaberPKETests> :check check_PKE_KeyGenDet_distinct
```

```
SaberKEMTests> :prove check_KEM_KeyGen_pk_length
SaberKEMTests> :prove check_KEM_KeyGen_sk_length
```

## Parameter sets

Constants are defined in `SaberConstants.cry`. To switch parameter sets, change the following three values:

| Parameter | LightSaber | Saber (default) | FireSaber |
| --------- | ---------- | --------------- | --------- |
| `l`       | 2          | 3               | 4         |
| `et`      | 3          | 4               | 6         |
| `mu`      | 10         | 8               | 6         |

Also update the sanity check expected sizes in `SaberConstants.cry` to match the chosen parameter set (see Table 8 of the spec for the correct values).

## Design notes

### Specification faithfulness over reference compatibility

This implementation follows the formal SABER specification (Algorithms 17-22) as closely as possible. In several places the C reference implementation (`indcpa.c`, `pack_unpack.c`, `cbd.c`) diverges from the written spec — for example in byte ordering for polynomial packing, the bit-interleaving trick used in centered binomial sampling, and the ordering of components within the public key, secret key, and ciphertext. This Cryptol specification follows the **spec**, not the reference implementation, meaning its byte-level output will differ from the NIST KAT vectors (which were generated from the C reference). The mathematical correctness — specifically the roundtrip properties — is verified directly.

### Deterministic variants

Both `PKE_KeyGenDet` and `KEM_KeyGenDet` accept explicit seeds rather than sampling randomly. This is necessary for testing and for the KAT framework. The non-deterministic variants (`PKE_KeyGen`, `KEM_KeyGen`, `KEM_Encaps`) use a fixed pseudo-random `RandBytes` function suitable only for testing — they should not be used in any security-sensitive context.

### Performance

The primary performance bottleneck is `PolyMul` (schoolbook polynomial multiplication in `R_q = Z_q[x]/(x^256+1)`), which is called many times during `MatrixVectorMul`. This makes each KEM roundtrip test expensive. Optimized multiplication (e.g. using NTT or Toom-Cook) is a known area for future work.

## Relationship to the SABER specification

Each function in this implementation corresponds directly to a numbered algorithm in the SABER Round 3 specification:

| Cryptol function | Spec algorithm                  |
| ---------------- | ------------------------------- |
| `PKE_KeyGenDet`  | Algorithm 17 (Saber.PKE.KeyGen) |
| `PKE_EncDet`     | Algorithm 18 (Saber.PKE.Enc)    |
| `PKE_Decrypt`    | Algorithm 19 (Saber.PKE.Dec)    |
| `KEM_KeyGenDet`  | Algorithm 20 (Saber.KEM.KeyGen) |
| `KEM_EncapsDet`  | Algorithm 21 (Saber.KEM.Encaps) |
| `KEM_Decaps`     | Algorithm 22 (Saber.KEM.Decaps) |
| `GenMatrix_Zq`   | Algorithm 15 (GenMatrix)        |
| `GenSecret_Zq`   | Algorithm 16 (GenSecret)        |
